Problem and objective2 / 9

Fixed cloud setups lock in cost and latency up front

Normally, deployment scripts hard-code which service goes on which server. Moving work between edge and cloud means rewriting infrastructure code. Here, placement is a separate data plan: the builder reads that plan and sets up both environments automatically.

Core idea: separate "what runs where" (solver) from "how to build it" (Terraform).
Explain why I set it up this way: hard-coding servers means editing scripts by hand whenever costs or user locations change. Separating the decision into a shared plan lets FIGARO swap topologies with the same fixed Terraform templates.

Safeguards and lessons6 / 9

Cost caps, auto-teardown, and real hardware lessons

Budget circuit breaker

The database tracks AI token spend and pauses API calls at $5.00. A background monitor watches combined compute and AI spend to auto-destroy cloud nodes.

Status: AI pause cap live;
guard monitor tested in dry-run

Auto-destruct on exit

Closing the local session or shutting down the PC triggers full AWS cleanup. An on-instance timer self-terminates idle cloud Spot nodes after 15 minutes.

Status: Full teardown verified ($0 AWS);
idle cloud timer validated offline

Containers over VMs

VMware Workstation blocked nested virtualization for full Proxmox VMs. Switching Proxmox to native Linux containers solved boot reliability cleanly.

Status: Edge container runs natively;
Terraform updated to default to LXC
Built so forgotten cloud instances cannot stay running when the laptop or VMware closes.
Talk through three practical issues I ran into and fixed. First: a $5 spending cap across AI tokens and Spot uptime. Second: auto-teardown — I ran the destroy script live and checked AWS afterwards ($0/hr left running, even with Proxmox turned off). Third: VMware hid nested virtualization (VT-x), so I switched the Proxmox edge setup from heavy QEMU VMs to lightweight Linux containers (LXC).

Choosing the right environment8 / 9

Proxmox Edge vs. AWS: solo testing now vs. team setup next

Proxmox Edge (Home / Shared Lab)

Zero cloud cost · Fast container loop
Pros: Free trial-and-error ($0/hr), quick container restarts, and the exact workflow I will reuse on the upcoming GPU server.
Cons: Currently tied to my single laptop on local Wi-Fi—shuts off with VMware and isn't reachable by external teammates.

AWS Milan Spot

Public reach · Real multi-user access
Pros: Always reachable by collaborators and phones on 4G/5G without port-forwarding; great for multi-user tests and real cloud APIs.
Cons: Bills by the hour (~$0.005–$0.015/hr) if forgotten and takes longer per clean cold boot (~3–5 min when built from source).

Now · Solo Testing & Playing

Default to Proxmox (All-Edge) for free, fast daily iteration. Spin up AWS Spot briefly only for external checks, then tear down.

Next · Teammates + GPU Server + FIGARO

Use the shared GPU server as Edge (hosting FIGARO & heavy models at $0/hr) and add AWS in Hybrid mode for teammate access & shared state.

Both options share the same container images and Terraform bridge—switching is one plan change.
Give a practical take on where it makes sense to run things today vs. next month. For solo experimenting right now, Proxmox edge is easier and free—no AWS clock ticking while debugging containers or Terraform scripts, and everything I practice in Proxmox transfers straight to the powerful GPU server later. Once teammates join and FIGARO + the GPU server are available, that shared GPU server becomes the team's fast edge host, while AWS fills in for public internet access and shared state across collaborators.
